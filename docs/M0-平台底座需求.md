# M0 平台底座 · 产品需求说明（v0.1）

> **文档性质**：产品最小范围说明，用于立项与表结构设计前的需求对齐。  
> **与主文档关系**：《Velrix-SpringBoot重写需求文档.md》为完整练习课表；本文仅定义 **第一版可交付、可演示** 的底座范围，技术增强项单列后续迭代。  
> **状态**：草案 v0.1  
> **最后更新**：2026-09-29

---

## 1. 背景与目标

### 1.1 背景

Velrix 类企业工作台由 **平台底座** 与 **业务模块**（主数据、库存、订单、流程等）组成。业务模块均依赖：统一登录、统一身份、统一菜单与操作权限、可扩展的审计能力。

若从零立项，不宜第一天按完整课表实现所有 R0 规则与中间件能力，应先交付 **可被业务模块挂载的最小平台**。

### 1.2 产品一句话

**内部业务人员使用的 Web 管理后台**：账号密码登录；不同角色看到不同菜单；未授权操作在后端被拒绝；管理员可配置用户、角色与菜单权限。

### 1.3 v0.1 目标

| 目标 | 说明 |
|------|------|
| 身份 | 明确「当前登录是谁」，账号可启用/停用 |
| 授权 | 通过角色分配菜单与操作权限；支持超级管理员 |
| 体验 | 登录后可获取菜单树与权限码，供前端渲染侧栏与按钮 |
| 安全底线 | 密码不明文存储；接口鉴权；前端隐藏按钮不构成授权 |
| 可追溯（最小） | 角色-菜单授权变更可追责 |

### 1.4 非目标（v0.1 不做）

- 任何业务域：商品、库存、采购/销售单、核销、流程引擎、通知、定时任务等  
- 多租户、多法人、客户/供应商门户、自助注册、OAuth/短信/MFA  
- 数据权限（按部门/仅看本人数据）、字段级权限、权限申请审批流  
- 登录失败锁定、Refresh Token、退出后 Token 黑名单、权限 Redis 缓存（见 §6 后续迭代）  
- 全量写操作审计检索与合规报表（仅约定最小审计范围，见 §3.6）

## 2. 用户与角色

| 角色 | v0.1 | 说明 |
|------|------|------|
| 系统管理员 | 必须 | 管理用户、角色、菜单；配置角色权限；通常具备超级管理员能力或等价账号 |
| 普通业务用户 | 必须 | 至少一个演示账号，用于验证菜单差异与接口拒绝 |
| 外部用户/匿名 | 不做 | — |

## 3. 功能需求

### 3.1 身份与登录

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-01 | 支持「登录名 + 密码」登录，成功后进入已登录状态（会话或 Token，实现阶段确定） | P0 |
| M0-F-02 | 未登录访问受保护资源被拒绝 | P0 |
| M0-F-03 | 停用账号不可登录；须明确提示或统一错误策略（避免泄露账号是否存在，可选） | P0 |
| M0-F-04 | 系统可解析当前用户身份（至少：用户标识、登录名、显示名） | P0 |
| M0-F-05 | 支持登出（清除服务端会话或使客户端放弃凭证）；v0.1 不要求旧凭证全局失效 | P1 |

### 3.2 用户管理（管理员）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-10 | 新增用户：登录名、显示名、初始/重置密码、启用状态 | P0 |
| M0-F-11 | 编辑用户：显示名、启用/停用、重置密码 | P0 |
| M0-F-12 | 为用户分配角色（见 §4 决策：单角色或多角色） | P0 |
| M0-F-13 | 用户列表与详情查询 | P1 |
| M0-F-14 | 物理删除用户 | 不做（v0.1 仅停用） |

### 3.3 角色与权限

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-20 | 角色的创建、编辑、列表（名称；是否超级管理员，见 §4） | P0 |
| M0-F-21 | 超级管理员：无需配置菜单即拥有全部菜单与操作权限 | P0 |
| M0-F-22 | 非管理员角色：通过勾选 **菜单树** 获得可见菜单 | P0 |
| M0-F-23 | 菜单项区分 **页面（菜单）** 与 **操作（按钮）**；操作权限以 **稳定权限码** 标识（如 `purchase-order:submit`），与前端路由解耦 | P0 |
| M0-F-24 | 角色授权为 **覆盖式保存**（一次提交替换该角色已有菜单/操作授权） | P0 |
| M0-F-25 | 后端对受保护接口校验权限码；无权限返回拒绝（建议 HTTP 403） | P0 |
| M0-F-26 | 仅授权子菜单时，**返回给前端的菜单树须包含祖先节点**，避免侧栏断裂 | P0 |

### 3.4 菜单管理（管理员）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-30 | 菜单树维护：父级、名称、前端路由 path、排序、是否隐藏 | P0 |
| M0-F-31 | 菜单类型：页面入口 / 按钮（操作） | P0 |
| M0-F-32 | 按钮类型节点携带权限码（可与 path 复用或独立字段，设计阶段定） | P0 |

### 3.5 当前用户工作台数据

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-40 | 提供「当前用户」聚合接口：用户基本信息 + 可访问菜单树 + 拥有的操作权限码列表 | P0 |
| M0-F-41 | 菜单树结构满足前端侧栏渲染（含祖先补齐后的树） | P0 |

### 3.6 审计（最小）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-50 | 记录 **角色-菜单/权限授权变更**：操作人、时间、目标角色、变更摘要 | P0 |
| M0-F-51 | 用户/角色/菜单的增删改全量审计 | P1（v0.2） |
| M0-F-52 | 业务单据审计 | 不做（归属业务模块） |

### 3.7 组织（部门）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| M0-F-60 | 组织树维护 | 可选，见 §4 决策 D7 |
| M0-F-61 | 用户挂载组织，仅展示或筛选 | 可选 |
| M0-F-62 | 按组织计算数据权限或审批人 | 不做（v0.1） |

## 4. 产品决策（表结构设计前须定稿）

设计数据模型前，由负责人确认以下选项并记入本文档修订记录。

| ID | 决策点 | 选项 | 建议（v0.1） | 备注 |
|----|--------|------|--------------|------|
| D1 | 用户与角色关系 | 单角色 / 多角色 | 多角色更贴近企业；练手可先单角色 | 影响关联表 |
| D2 | 超级管理员 | 角色标记 `is_administrator` / 内置账号 | 角色标记 + 至少一个种子管理员 | 授权逻辑是否绕过菜单表 |
| D3 | 权限码载体 | 独立 code 字段 / 与菜单 path 复用 | 稳定字符串，不与 URL 强绑定 | 改路由不丢权限 |
| D4 | 菜单层级 | 2～3 层（模块→页面→按钮） | 至少支持 parent 树 | — |
| D5 | 用户删除策略 | 仅停用 / 物理删除 | **仅停用** | 与后续主数据「停用」一致 |
| D6 | 登录名大小写 | 敏感 / 不敏感 | **不敏感** | 是否增加规范化字段 |
| D7 | v0.1 是否含组织 | 不含 / 含组织仅展示 | 半年内做审批则可选「含组织仅展示」 | `org_id` 是否进首版表 |
| D8 | 审计 v0.1 范围 | 仅角色授权 / 含用户角色菜单变更 | **至少角色授权** | 审计表字段粒度 |

## 5. 验收场景（演示剧本）

以下场景全部通过，视为 **M0 v0.1 产品验收通过**（与《Velrix》AC0-x 部分对齐，不要求 Redis/JWT 黑名单）。

| 编号 | 场景 | 预期结果 |
|------|------|----------|
| AC-M0-01 | 管理员登录 | 可见用户/角色/菜单等管理入口 |
| AC-M0-02 | 新建角色「采购员」，仅勾选采购相关菜单及一个「提交」操作权限 | 保存成功 |
| AC-M0-03 | 新建用户「李四」，仅分配采购员角色 | 保存成功 |
| AC-M0-04 | 李四登录 | 侧栏仅采购相关菜单；`/me` 类接口含对应权限码 |
| AC-M0-05 | 仅授权子菜单时李四拉取菜单树 | 树中包含该子菜单的祖先节点 |
| AC-M0-06 | 李四调用需 `purchase-order:submit` 的接口 | 成功（若已授权） |
| AC-M0-07 | 李四调用仅管理员可用的接口 | 被拒绝（403 或项目统一错误码） |
| AC-M0-08 | 管理员修改采购员角色权限 | 产生一条可查询的授权变更审计记录 |
| AC-M0-09 | 停用李四后尝试登录 | 登录失败 |
| AC-M0-10 | 未登录访问受保护接口 | 401 或项目统一未认证响应 |

**与完整课表差异说明：**

- AC0-3（退出后旧 Token 无效）→ 列入 §6，非 v0.1 必测  
- AC0-2 与 AC-M0-07 等价

## 7. 接口清单（逻辑级，路径可微调）

实现阶段须与统一响应约定对齐（见主需求文档 §3.4）。

| 方法 | 路径（建议） | 说明 | v0.1 |
|------|----------------|------|------|
| POST | `/api/auth/login` | 登录 | P0 |
| POST | `/api/auth/logout` | 登出 | P1 |
| GET | `/api/me` | 当前用户 + 菜单树 + 权限码 | P0 |
| CRUD | `/api/users` | 用户管理 | P0 |

## 8. 概念模型（非物理表）

便于表设计前的领域名词对齐：

```text
用户 (User) ──N:M──► 角色 (Role) ──N:M──► 菜单 (Menu)
                         │
                         └── 超级管理员 → 隐含全部 Menu/权限

菜单：树形；类型 = 页面 | 操作；操作携带权限码

审计：授权变更事件（谁、何时、对哪个角色、摘要）

组织 (Org)：树形；用户可选归属（若 D7 启用）
```

物理表命名与字段在 **《M0 数据模型》** 或 Flyway 设计中单独产出，须满足主文档 §3.3 数据约定（金额本阶段无；枚举存字符串；时间精度等在后继模块统一）。

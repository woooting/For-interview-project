## 1. M1 是什么：ERP 的"名词字典"

```
M0 平台底座（已完成）：谁能登录、谁能干什么 —— 用户/角色/权限/审计
M1 主数据（本模块）  ：业务上有哪些名词 —— 商品/仓库/库位（客户/供应商待 T4）
M2 库存（未来）      ：名词上发生的数量变动 —— 入库/出库/流水
M3 订单（未来）      ：名词串成的交易 —— 采购单/销售单
```

依赖单向向下：M2/M3 引用 M1 的数据，M1 用 M0 的权限体系。

### 两条铁律（解释 M1 几乎所有"怪设计"）

1. **主数据只停用、不物理删除。** 历史单据引用的商品不能"消失"，否则报表全乱。退役 = `INACTIVE`。
2. **删之前必须知道谁在用它。** 引用影响查询（impact）为此而生；DELETE 永远 409（见 §4）。

### 数据骨架（V17–V19 四张表）

```
md_product                 md_warehouse
┌─────────────────┐        ┌─────────────────┐
│ code（原样展示）  │        │ code / code_norm │
│ code_norm  UQ    │        │ name / address   │
│ name / unit      │        │ status           │
│ status           │        └────────┬────────┘
│ batch_managed    │                 │ 1:N
│ serial_managed   │        md_location
│ max_inventory_qty│        ┌─────────────────┐
└────────┬────────┘        │ warehouse_id  FK │
         │                 │ code / code_norm │ ← 唯一约束 (warehouse_id, code_norm)
         │                 │ name / status    │   即"同一仓库内"编码唯一，跨仓库可重名
         │                 └────────┬────────┘
         │                          │ 1:N
         │        md_location_capacity（容量 = 库位×商品的上限）
         │        ┌────────────────────────────┐
         └────────┤ (location_id, product_id) PK │
                  │ max_qty DECIMAL(18,6) > 0    │
                  └──────────────────────────────┘
```

- **`code` 管给人看，`code_norm` 管给机器比**：展示保留用户原样（`sku-01`），唯一性与查重走 trim+大写后的标准形（`SKU-01`）。
- **容量表联合主键**天然防重复配置；FK RESTRICT 在数据库层兜底"有容量的库位删不掉"。

## 2. 一次写请求的七站旅程

以 `POST /api/products`（创建商品）为例：

```
①JwtAuthFilter          ②RequirePermInterceptor      ③DTO 校验(@Valid)
   (M0)                     (M0)                        (@NotBlank)
      │                        │                           │
   验 JWT 认出用户      查 Redis 权限：有 product:create 吗      字段形状检查 → 400
   没登录 401            没有 403
   │                        │                           │
   ▼                        ▼                           ▼
④ProductController ──→ ⑤ProductService ──→ ⑥Mapper ──→ ⑦MySQL
  薄搬运层                 业务心脏            SQL        uk(code_norm) 兜底
  补 actor/ip 两个          prepare(): 规范化/查重/组装
  审计参数                  + insert + 审计
```

- **④ Controller 不写业务规则**，只把 HTTP 翻译成 Service 调用，并补上 `WebActor.username()` / `clientIp()` 两个审计参数。
- **⑤ Service 是所有业务规则的执行者**：规范化 → 查重（更新时 `ne(id)` 排除自己）→ 组装（默认 ACTIVE）→ insert → 审计。
- **⑦ 双保险的原理**：Service 查重挡不了并发——`selectOne`（check）和 `insert`（act）之间有时间窗，普通 SELECT 不加锁，两个事务可以同时通过检查。这**与隔离级别基本无关**（RC 同样中招），是 check-then-act 竞态。唯一索引防它的原理不同：**查询不锁行，索引锁写入**——第二个 insert 阻塞在第一个事务的索引锁上，提交后立刻 duplicate key。代码查重给友好提示（422），索引保证并发正确性。
- 各站异常（401/403/400/422/409）由 `GlobalExceptionHandler` 统一翻译成 HTTP + `ApiResponse` 壳。

**校验分层契约**（当前定稿）：

| 层 | 管 | 不管 | 失败形态 |
|---|---|---|---|
| DTO `@Valid` | 字段形状：空值/范围 | 一切需要查库的 | 400 `PARAM_INVALID`，字段级消息 |
| Service | 业务：唯一性/状态/存在性/批内重复 | — | 422 `BIZ_ERROR` 或 409 `BIZ_CONFLICT` |
| DB 索引 | 并发兜底 | — | `DuplicateKeyException` → 422 |

Service 与 DTO 重复的空值检查已砍除；service 契约 = **调用方保证非空**（Controller 是唯一入口）。

## 3. 四条核心业务规则

根规则 + 三个衍生执法的结构：

```
R1 状态机（根）        每条主数据只有 ACTIVE / INACTIVE
  ├─ R2 冻结联动       仓库 INACTIVE → 名下所有库位的写操作冻结
  ├─ R3 可入库组合     仓库 ACTIVE ∧ 至少一个库位 ACTIVE → 才可入库（给 M2）
  └─ R4 容量门禁       配容量时商品必须 ACTIVE；库位停用后容量封存
```

- **R1**：停用的语义是"不能用于新业务"，不是"消失"——列表仍展示（按状态筛选）。执法者是 Guard，M1 不预设未来有哪些业务，只提供检查点。
- **R2 冻结联动**：`WarehouseReadinessPolicy.isWarehouseFrozen` 一处定义，`LocationService` 四个写方法（建/改/启停/删库位）入口各调一次。方向**只有父→子**：库位停用不影响仓库与兄弟库位。
- **R3 可入库组合**（`WarehouseGuard.requireActiveForInbound`，三段式）：仓库不存在 → 仓库停用 → 无可用库位。第三段是聚合判断（`isInboundReady`），同时被列表的 `inboundReady` 标志复用——**一处定义两处消费**，所以住在 Policy 而非 Guard。
- **R4 容量覆盖**（`PUT /api/locations/{id}/capacities`）：前置两道门——**仓库冻结检查（看父）**与**库位自身状态检查（看自己）**是两条独立规则（`LocationService.java:158-163`），谁也不能替谁把关。语义为全量替换：批内校验（商品不重复、`productGuard.requireActive`）→ 同一事务内 delete 全部旧行 + insert 新列表。不做 diff：前端每次提交完整表单，全量替换天然幂等，整单失败不留半套配置。

## 4. 删除保护：impact 闭环

前端删除 = **两次请求**：先 `GET /{id}/impact` 弹窗展示明细，确认后 `DELETE /{id}`——服务端**必须再查一遍**（展示与确认之间数据可能变化，安全决策基于服务端当下数据）。

两次请求汇到同一处 `MasterDataImpactService.summarize(kind, id)`：

```
启动期（一次）：Spring 扫描 @Component → 所有 Contributor Bean 收集为 List
             → 构造器按 kind() 分组成 EnumMap → 单例入池
运行期（每次）：查表 contributorsByKind.get(kind)
             → 逐个 contributor.contribute(entityId)  ← 谁引用谁上报，无引用返回空列表
             → items.isEmpty() == deletable
```

- **Contributor 约定**：无引用返回空列表而非 count=0 项 → 聚合层保持傻瓜化（有话=有引用）。"在库 quantity=0 视为无引用"的判定因此落在 M2 的 Contributor 侧。
- **ImpactItem.quantity** 是 M2 预留特例（在库量要报数值），当前用 `of(refType, label, count)` 三参工厂传 null。
- **DELETE 落点**：有引用 → 409 + 分类型明细；无引用 → **也 409**（"请使用停用"，D2 定稿）。409 而非 422 是告诉前端"资源状态不允许，message 可直接展示给用户"。
- **测试分层**：`ProductServiceTest` mock 掉 `summarize` 测 409 行为；`MasterDataImpactServiceTest` 手动 `new` 传 mock List 测分组聚合——手动 new 就是手工扮演 Spring 的集合注入。

## 5. 横切与接缝

### 审计链路

`MasterdataAuditWriter` 是 M0 `sys_audit_log` 的薄封装：`actor / action / targetType / targetId / summary / ip` 六要素，summary 截断 512。与业务**同事务**：审计记录 = 真实发生过的写操作。action 命名集中（`MD_PRODUCT_CREATE/UPDATE/STATUS/DELETE`、`MD_LOCATION_BATCH_CREATE`、`MD_LOCATION_CAPACITY_REPLACE`…）。

### 权限供给线（`@RequirePerm` 的完整一生）

```
开发期：V20/V21 种子把 perm_code 挂在 sys_menu 的 BUTTON 节点上（2200 段）
        菜单树既是前端导航也是权限载体（MENU 管导航，BUTTON 管权限）
配置期：sys_role_menu 给角色勾节点 → sys_user_role 给用户派角色
运行期：JwtAuthFilter 认出 userId → RequirePermInterceptor 读注解
        → menuAccessService.hasPerm：先 Redis 缓存，miss 查库回填
        → 管理员改授权发 MenuChangedEvent → 缓存失效重查
```

**新增按钮权限三步缺一不可**：迁移插菜单节点 → 管理员给角色勾上 → 方法标 `@RequirePerm`。

### 与 M2/M3 的双向接缝

出向（M2 入库时调 M1，规则全在 M1 侧）：

```java
productGuard.requireActive(productId);                 // M1-F-30
warehouseGuard.requireActiveForInbound(warehouseId);   // AC1-2，三段式
locationGuard.requireBelongsToWarehouse(locId, whId);  // 防串仓
capacityQuery.getMaxQty(locId, productId);             // M1-F-33
```

入向：M2/M3 各写 `@Component` 实现 `MasterDataImpactContributor`，impact 自动变准。

端口与 Stub（依赖倒置）：`application/port/LocationOccupancyQuery` 是 M1 声明的"我需要库位占用量"，当前由 `infrastructure/stub/StubLocationOccupancyQuery`（永远无占用）撑着，M2 提供真实现后替换。分清两词：

| | 管什么 | 谁实现 |
|---|---|---|
| `LocationCapacityQuery` | 容量**上限**（配了多少） | M1（容量表） |
| `LocationOccupancyQuery` | 当前**占用**（用了多少） | M2（现为 Stub） |

M2 入库公式：`occupancy + 本次数量 ≤ capacity`，各查各的模块，互不直查对方表。

## 6. 全景一张图

```
M0 底座 ──用户/角色/菜单/审计/Redis ─────────────────────────┐
                                                            │ 认证、权限、审计
M1 主数据                                                    ▼
  数据：product / warehouse / location / capacity（V17–V19）
  规则：状态机 → 冻结联动 → 可入库组合 → 容量门禁
  保护：code_norm 唯一（Service 查重 + DB 索引双保险）
  删除：impact SPI 聚合 → 永远 409（有引用给明细，无引用劝停用）
  旅程：JWT → 权限(Redis) → DTO 校验 → Controller → Service → DB
                                                            ▲
M2 库存（未来）──────────────────────────────────────────────┤ 调 Guard/容量
  入库 = requireActiveForInbound + occupancy ≤ capacity        │ 注册 InventoryContributor
  库存表 = OccupancyQuery 真实现 ─────────────────────────────┘
M3 订单（未来）：Customer/Supplier Guard + PO/SO Contributor（T4 先建客户/供应商档案）
```

**T4 开工自检**：为什么建客户表要同时建 `CustomerGuard` 和 `CustomerImpactContributor`？——Guard 是 M3 下单的门禁（出向接缝），Contributor 是 M3 单据引用的回报口（入向接缝）。主数据建档的意义 = 被下游安全地使用、被安全地退役。
